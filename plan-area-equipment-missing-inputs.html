HAC Status Indicator — Surface Incomplete Area/EquipmentItem Inputs

Make new Area and EquipmentItem items "start empty" (no placeholder numeric HAC values) and reuse the existing failedItems / CalculationFailureModal machinery to tell users exactly which fields are missing before a HAC calculation can succeed.

01 Executive Summary

The HAC status indicator (components/dashboard/hac-status-indicator.tsx) currently tells users when they need to build the study tree down to Zone level to enable a HAC calculation. Once the tree reaches Zone level, however, the indicator gives no help identifying which items (Area, EquipmentItem, Scenario, Zone) still have incomplete or invalid inputs preventing a successful calculation.

Today, new Area and EquipmentItem items are created with fully-populated numeric HAC defaults (defaultArea.hac, defaultEquipmentItem.hac in app/types/firestore.tsx), so they calculate "successfully" with made-up placeholder numbers (e.g. length: 10, ambientTemperature: 288.15, pressure: 101325) that the user never consciously entered. This is inconsistent with Scenario, which starts as hacType: "None" — a deliberate "not configured" sentinel that the calculation engine already treats as "never-calculated" rather than success/failure.

The agreed approach: make Area and EquipmentItem "start empty" on creation (no placeholder numeric values), and let the existing failedItems / calculation-failure-modal.tsx machinery surface "Missing: Length, Breadth, Height, ..." style messages — the same way scenario gas-release calculations already do today via the "Missing or invalid inputs: x, y, z" error convention (see lib/bscalculations/scenario/bs-gas-calculations.ts:81-89, already parsed by sanitizeError in components/dashboard/calculation-failure-modal.tsx:30-31).

No new schema discriminator (no hacType on Area/EquipmentItem), no new display state, no new "incomplete items" concept — this is a scoped, additive change: relax a handful of required numeric fields to optional, trim the "new item" templates, and add validation guards so the calculation engine throws a clear, well-formatted error instead of producing NaN or null-spread results.

Net Effect for the User

New behaviour
  • New Area → calculates immediately, fails with "Missing: Length, Breadth, Height, Blockage Factor, Volume Air Flow Rate, Ambient Temperature, Ambient Pressure" → shows in the HAC status indicator's failure modal → click-through opens the Area HAC form.
  • New EquipmentItem → fails with "Missing: Material" → same modal, click-through opens the EquipmentItem HAC form.
  • Scenario (hacType: "None") → unchanged, "never-calculated", not a failure.
  • Existing fully-populated Firestore documents → unaffected (optional fields remain valid when present).
Current behaviour
  • New Area calculates "successfully" using made-up placeholder numbers the user never entered (10m × 10m × 5m room, 15°C, 1 atm, etc.)
  • New EquipmentItem calculates "successfully" with material: "" — silent no-op spread of null equipment results, stale/empty outputs
  • HAC status indicator shows "in-sync" / "out-of-sync" for items the user hasn't actually configured
  • No guidance pointing the user at which item or field needs attention

03 Before / After Behaviour

Before
  • New Area's hac object is fully populated: length: 10, breadth: 10, height: 5, ambientTemperature: 288.15, ambientPressure: 101325, blockageFactor: 0, volumeAirFlowRate: 1
  • Calculation "succeeds" immediately using these placeholder numbers — user never entered them
  • New EquipmentItem has hac.material: "" — calculateEquipmentItemResults("") returns null, but {...null} is a no-op spread, so the calculation reports success: true with stale/empty outputs
  • HAC status indicator shows "in-sync"/"out-of-sync" for items the user hasn't configured — no signal that inputs are placeholder data
After
  • New Area's hac object omits the 7 numeric fields entirely — only ventilationLocation, ventilationDirection, unit fields, and notes remain
  • validateAreaInputs throws "Missing or invalid inputs: length, breadth, height, blockageFactor, volumeAirFlowRate, ambientTemperature, ambientPressure" — surfaces as calculationState.status === "failed"
  • New EquipmentItem's hac.material remains ""; calculation now throws "Missing or invalid inputs: material" instead of silently succeeding
  • failedItems picks up both via existing isRootCauseFailure() logic; CalculationFailureModal's sanitizeError() renders "Some required fields are incomplete — Click to open and review the inputs."
  • Clicking the failed item navigates to its HAC form (requestedFormTab: "hac") — existing navigation wiring, no change needed

2a — validateAreaInputs: missing-fields check

Current implementation only validates bounds when fields are present — it does not check presence. Add a presence check that collects all missing required fields and throws a single "Missing or invalid inputs: ..." error, following the exact convention in bs-gas-calculations.ts:81-89.

lib/bscalculations/validate-inputs.ts
const REQUIRED_AREA_HAC_FIELDS: Array<keyof Area["hac"]> = [
  "length",
  "breadth",
  "height",
  "blockageFactor",
  "volumeAirFlowRate",
  "ambientTemperature",
  "ambientPressure",
];

export function validateAreaInputs(hac: Area["hac"]): void {
  const missingFields = REQUIRED_AREA_HAC_FIELDS.filter(
    (field) => hac[field] == null
  );

  if (missingFields.length > 0) {
    throw new Error(`Missing or invalid inputs: ${missingFields.join(", ")}`);
  }

  validateTemperature(hac.ambientTemperature, "ambientTemperature");
  validatePressure(hac.ambientPressure, "ambientPressure");
}
  • Order of REQUIRED_AREA_HAC_FIELDS determines error message field order — pick an order matching the Area HAC form's field order (length, breadth, height, blockageFactor, volumeAirFlowRate, ambientTemperature, ambientPressure mirrors schema declaration order)
  • Use plain Error, not ValidationError — bs-gas-calculations.ts uses plain Error for this exact "Missing or invalid inputs:" pattern. Grep for instanceof ValidationError before finalizing to confirm nothing special-cases this.
  • == null (not !hac[field]) correctly treats blockageFactor: 0 as present (valid value), not missing

2b — EquipmentItem material validation

calculateEquipmentItemResults returns Material | null — null when material is empty or not found, logging via console.error but not throwing. The caller currently does {...equipmentResults}, which is a JS no-op when equipmentResults is null — calculation silently "succeeds" with stale/empty outputs. This is the bug to fix.

export function validateEquipmentInputs(equipment: EquipmentItem): void {
  if (!equipment.hac.material) {
    throw new Error("Missing or invalid inputs: material");
  }

}
