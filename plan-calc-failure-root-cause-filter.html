Calculation Failure Modal — Root-Cause Filter

Branch: feat/auto-hac-calculation  ·  2026-05-28  ·  nEXus

The calculation failure modal currently lists every item in the study tree with calculationState.status === "failed", including cascade descendants (items that failed because an ancestor failed) and upstream-dependency items (items waiting for a parent's outputs). This creates noise that buries the actual input errors the user must fix.

This change filters failedItems in useAutoCalculation to expose only root-cause failures — items with genuine missing or invalid inputs — directing the user straight to the form fields that need attention. The badge count, modal description, and indicator state all update to reflect the root-cause count only. When no root-cause failures remain, the indicator shows succeeded even if cascade failures are still present in the tree (they will clear automatically on the next calculation run).

Architecture & Data-Flow

Current flow (all failures shown)

studyItems (Firestore) │ ▼ markDescendantsFailedForFailedItems() │ sets engineVersion = "dependency-failure" on all descendants ▼ useAutoCalculation → failedItems useMemo │ DFS, collects EVERY item where status === "failed" │ ● root-cause validation failures ← should show │ ● dependency-failure cascade items ← should HIDE │ ● upstream dependency error items ← should HIDE ▼ AutoCalculationState.failedItems (unfiltered array) │ ├─▶ HacStatusIndicator badge (shows total count) └─▶ CalculationFailureModal (lists all items)

Proposed flow (root-cause only)

studyItems (Firestore) │ ▼ markDescendantsFailedForFailedItems() │ sets engineVersion = "dependency-failure" on all descendants ▼ useAutoCalculation → failedItems useMemo │ DFS + isRootCauseFailure() filter │ ● engineVersion === "dependency-failure" → SKIP │ ● error matches dependency regex patterns → SKIP │ ● everything else → INCLUDE ▼ AutoCalculationState.failedItems (root-cause only) │ ├─▶ HacStatusIndicator badge (shows root-cause count) │ ├─ length > 0 → "failed" state, clickable button │ └─ length = 0 → "in-sync" / "out-of-sync" (succeeded UX) └─▶ CalculationFailureModal (lists root-cause items only)

isRootCauseFailure — filter predicate

Module-level helper in use-auto-calculation.ts. Not exported (internal to the hook file).

function isRootCauseFailure(state: CalculationState): boolean {
  // Explicit cascade mark set by markDescendantsFailedForFailedItems()
  if (state.engineVersion === "dependency-failure") return false;

  const msg = state.error?.message ?? "";

  // Upstream dependency errors: item waiting for a parent's computed outputs.
  // These mirror the "dependency" branch in the modal's sanitizeError().
  if (/equipment item outputs are undefined/i.test(msg)) return false;
  if (/area outputs are undefined/i.test(msg))           return false;
  if (/airchangerate or effectivevolume is undefined/i.test(msg)) return false;
  if (/lflvol or molecularweight is undefined/i.test(msg))       return false;

  return true;
}
Note: The regex patterns mirror exactly the four "dependency" branches in sanitizeError() inside calculation-failure-modal.tsx. Both functions must stay in sync if new dependency error messages are added to the engine. A comment cross-referencing them is recommended.

Before / After Behaviour

Scenario: Scenario S is missing pressure input

Tree: Study → Area A → Equipment E → Scenario S → (no children)

Before

  • Area A shown — "waiting for parent equipment calculation" (amber)
  • Equipment E shown — "waiting for parent area calculation" (amber) or similar
  • Scenario S shown — "missing required properties" (red) ✓ correct
  • Any zone children of S shown — "not calculated because ancestor S failed" (red)
  • Badge count: 4

After

  • Area A hidden (dependency error → not root cause)
  • Equipment E hidden (dependency error → not root cause)
  • Scenario S shown — "missing required properties" (red) ✓
  • Zone children hidden (engineVersion === "dependency-failure")
  • Badge count: 1

Scenario: User fixes Scenario S — cascade failures still in tree, re-calc not yet run

Before (after fix, pre re-calc)

  • Modal still showed Area, Equipment, Scenario, zone children
  • Badge count still 4 (confusing — S is "fixed" but badge unchanged)

After (after fix, pre re-calc)

  • Scenario S no longer has a validation failure → filtered list = empty
  • Badge count: 0 → indicator shows green "in-sync" or "out-of-sync"
  • Button not shown (no root-cause items to navigate to)
  • Cascade failures remain in tree but are invisible to the user

Scenario: syncStatus === "failed" with no root-cause failures

Before

  • Button rendered with badge "0"
  • Clicking opened an empty modal

After

  • || syncStatus === "failed" removed from displayState logic
  • Non-clickable span rendered (green or clock icon)
  • Empty modal is never reachable

Risks

LOW Regex drift

If the calculation engine adds new dependency error messages that don't match the four regex patterns, those items will appear as root causes. Mitigated by the cross-reference comment added in Phase 1A. Same risk exists today for sanitizeError.

LOW syncStatus removal

Removing || syncStatus === "failed" from displayState changes an existing edge case (empty failedItems + syncStatus failed → button). This was a confusing UX state with no practical path to it in normal usage. One test updated to reflect the change.

LOW "Green after fix" window

After the user corrects an input but before re-calculation runs, the indicator shows green while cascade failures are still in the tree. This is intentional (decision 7a) — the cascade items are not actionable by the user. The debounce is 1 s so the re-calc fires quickly.

Open Decisions / Future Considerations

Shared dependency-error utility

The four dependency regex checks are currently duplicated between isRootCauseFailure() (new, in the hook) and sanitizeError() (existing, in the modal). For now they are kept separate (hook is filtering logic; modal is display logic), with a cross-reference comment to prevent drift. A future refactor could extract a shared lib/calculation-error-category.ts if the list of patterns grows significantly.

Engine-level discrimination

Currently only downstream cascade failures use a dedicated engineVersion field ("dependency-failure"). Upstream dependency errors are distinguished only by error message text. A future improvement could have the engine or helper functions set a distinct engineVersion (e.g., "upstream-dependency") for upstream errors, removing the need for text matching entirely.
