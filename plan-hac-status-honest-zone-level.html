Implementation Plan

Make the HAC Status Indicator Honest — require a real zone-level result

The sidebar HAC status shows a green "calculation complete" check when a study is only developed to Area level, or when a Scenario's HAC type isn't even chosen. This plan makes the existing sync-status logic tell the truth: green only when at least one real, current zone classification exists — without inventing any new "completeness" concept, touching exports, or reverting the auto-calculation UX.

1 Executive Summary

The bug. The indicator reads getSyncStatusLabel(studyRoot, studyItems). Its rollup reports the worst per-item sync label across all calculable descendants, which conflates "every existing item calculated without error" with "a real HAC result exists." So an Area whose own calculation succeeded — with no Zone beneath it — rolls up as in-sync. Likewise a BS EN 60079-10-1 zone with no dispersionType returns success:true with empty outputs, and still reads green.

The fix. Extend the existing never-calculated logic (which already special-cases Scenario hacType:"None") so the green check requires ≥1 real, current zone result and nothing stale/failed. The change lives in one shared module so the top indicator and per-item tree icons stay consistent. No new state, no new DisplayState, no export change, no Firestore migration.

In scope

  • Honest labels in lib/calculation-versioning.ts
  • Ripple to all four getSyncStatusLabel consumers
  • Unit + consumer tests; new createZone fixture

Explicitly NOT in scope

  • Reverting to the manual RunHACButton
  • Any formal "study complete" concept or new UI state
  • canExportSafely / report export gating
  • Changes to persisted calculationState

5 The Three Honest-Label Rules

Rule 1 — Scenario with unset HAC type → never-calculated

The existing block in getDirectSyncStatusLabel already forces hacType:"None" → never-calculated. Extend the same if (item.type === "scenario") block to also return never-calculated when hac?.hacType is undefined/empty (the new "start empty" state).

Gating on hacType alone is sufficient — releaseType is only meaningful within the BS discriminated union, and an unset hacType already covers "nothing chosen." Avoids over-reaching into the union.

Rule 2 — define "real zone result" (new pure predicate)

// local to calculation-versioning.ts — exhaustive switch so a future
// hacType literal is a visible gap, not a silent miss.
function zoneHasRealResult(zone): boolean {
  if (!isOutputInSync(zone)) return false;   // stale/failed never counts
  const hac = zone.hac, out = zone.outputs;
  switch (hac?.hacType) {
    case "BS EN 60079-10-1":
    case "Phast":
    case "User-defined":
      return Number.isFinite(out?.hazardDistance);  // empty {} ⇒ false
    case "Interior":
      return out?.zoneType != null;             // deliberate classification
    case "None":
    default:                                       // None / undefined
      return false;
  }
}

Backed by bs-calculation-service.ts (871–976): a BS zone with no dispersionType yields outputs = {} while still returning success:true — exactly the false-green case this catches.

Rule 3 — rollup requires a real, current zone

In getRollupSyncStatusLabel, after computing worstLabel: if it would be in-sync but no descendant zone satisfies zoneHasRealResult, downgrade to never-calculated. Reuse the descendant indices already enumerated by the rollup (or getDescendantItemsByType(root,"zone",items)). Applies to all rollup types. Preserve the existing container branch that returns never-calculated for zero calculable descendants.

9 Edge Cases & Invariants to Preserve

  • Empty new study (zero calculable descendants) must stay never-calculated — preserve the existing container-rollup branch.
  • failed / calculating / out-of-sync must still dominate in-sync — only downgrade an in-sync verdict, never upgrade a worse one.
  • A real current zone in one branch must not be masked by an unrelated unconfigured branch beyond existing severity rules — the guard is "≥1 real zone + nothing worse," no stricter.
  • Zones nest under Area, EquipmentItem, or Scenario (study-tree-hierarchy.tsx 7–10) — zone discovery must cover all three parentages (descendant search already does).
  • Stale/failed zone must not count — gate zoneHasRealResult on isOutputInSync(zone), else a stale green sneaks back.
  • Ignition sources are calculable but not part of the zone chain — they must not satisfy the guard; their own failures keep surfacing via existing failedItems.
