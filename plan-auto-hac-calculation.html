Auto HAC Calculation

nEXus — Implementation Plan

BS EN 60079-10 · Auto-Calculation Feature

Context

nEXus currently requires users to manually press a "Run HAC" button to trigger calculations after editing any input field. The calculation engine is fast (< 2 seconds for most studies). The calculation-versioning module already detects every HAC-relevant field change and marks items out-of-sync — all the detection infrastructure needed for auto-calculation is already in place.

The goal is to remove the manual button and replace it with an auto-calculation system that fires automatically after a debounce whenever inputs change, plus a persistent toolbar status indicator showing the study's current sync health.

3. Fire callback from saveFormData (~line 1249, before return inside if (hasChanges))

if (this.hacRelevantChangeCallback) {
  const cb = this.hacRelevantChangeCallback;
  queueMicrotask(() => cb());
}
Why queueMicrotask? saveFormData is a synchronous method that mutates this._studyItems directly, then calls notifyStateChange() which triggers a React re-render via stateChangeCallback. Firing the HAC callback synchronously inside saveFormData would call into hook state setters (setIsPending) in the middle of the provider's own mutation sequence. queueMicrotask defers the call until after the current synchronous execution completes — consistent with the existing queueMicrotask usage in emitSelectionChanged (line 707).

Internal state

const [isPending, setIsPending] = useState(false);

Ref sync effects (MUST appear before other effects)

// Keep refs current so runCalculation (stable useCallback) always reads the
// latest provider/db — critical when the user switches studies.
useEffect(() => { dataProviderRef.current = dataProvider; }, [dataProvider]);
useEffect(() => { dbRef.current = db; }, [db]);
Why refs for dataProvider/db? runCalculation has empty deps [] (stable callback) and reads all mutable values through refs. Without these sync effects, after the user switches to a different study dataProviderRef.current would point to the old provider — causing calculations to write results to the wrong study tree and persist stale data to Firestore.

Load trigger effect

useEffect(() => {
  const studyIndex = dataProvider.getStudyIndex();
  if (studyIndex === "root") return;
  const { canExport } = canExportSafely(studyIndex, dataProvider.studyItems);
  if (canExport) return; // already in sync

  const timer = setTimeout(() => runCalculation(true), 300);
  return () => clearTimeout(timer);
}, [dataProvider, runCalculation]);
// dataProvider changes identity when a new study is loaded → effect re-fires correctly
// Note: the load trigger calls runCalculation(true) directly — it does NOT set isPending
// first. The indicator goes straight from no-state to isCalculating (blue spinner). The
// amber "pending" spinner is only shown during a user-initiated debounce window.

HAC change callback registration

useEffect(() => {
  dataProvider.setHacRelevantChangeCallback(() => {
    setIsPending(true);
    if (debounceTimerRef.current) clearTimeout(debounceTimerRef.current);
    debounceTimerRef.current = setTimeout(() => {
      debounceTimerRef.current = null;
      runCalculation(false);
    }, debounceMs);
  });
  return () => {
    dataProvider.setHacRelevantChangeCallback(undefined);
    if (debounceTimerRef.current) {
      clearTimeout(debounceTimerRef.current);
      debounceTimerRef.current = null;
    }
    // Reset transient UI state when the study switches. Without this, a pending
    // debounce that was cancelled still shows the amber spinner on the new study.
    setIsPending(false);
    setIsCalculating(false);
  };
}, [dataProvider, debounceMs, runCalculation]);

runCalculation — stable async callback (reads only from refs)

Stable callback constraint: runCalculation uses useCallback([], []) — empty deps. It must read all changing values exclusively through refs (dataProviderRef.current, dbRef.current). Never read React state or props directly inside this function. Future additions must also go through refs. 
const runCalculation = useCallback(async (isLoadTrigger: boolean) => {
  const provider = dataProviderRef.current;
  const studyIndex = provider.getStudyIndex();
  if (studyIndex === "root") return;

  const planAnchor = isLoadTrigger ? studyIndex : provider.selectedItem.index;
  // Note: for edit-triggered calcs, planAnchor is resolved at debounce-fire time
  // (not at callback time), so it reflects the item selected when the debounce expires.

  const plan = buildCalculationPlan(planAnchor, provider.studyItems);
  if (plan.length === 0) return;

  setIsPending(false);
  setIsCalculating(true);

  const studyItemsAtRequest = provider.studyItems;
  const requestedAt = new Date().toISOString();
  const requestedRevision = studyItemsAtRequest[planAnchor]?.inputRevision ?? 0;
  const { requestedRevisions, previousCalculationStates } =
    buildCalculationRequestMetadata(plan, studyItemsAtRequest);

  // Mark plan items as "running" in the tree BEFORE the fetch.
  // This transitions their calculationState.status to "running", which:
  //   (a) empties the failedItems memo during the calculation, and
  //   (b) shows the "calculating" sync status in the indicator.
  provider.setTreeItems(buildRunningItems(
    plan, provider.studyItems, requestedRevisions, requestedRevision, requestedAt
  ));

  try {
    // Fetch body mirrors the existing RunHACButton fetch in run-hac.tsx.
    // The body must include the running study items (post-buildRunningItems) so
    // the server sees the current inputRevisions. Mirror run-hac.tsx exactly:
    const response = await fetch("/api/bs-calculation/batch", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        items: provider.studyItems,   // current items (already marked running)
        plan,                          // ordered index array from buildCalculationPlan
        studyIndex,
      }),
    });

    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    const result = await response.json();

    // Merge logic — mirrors run-hac.tsx lines 168–246. Steps in order:
    //  1. detectInputChanges(plan, studyItemsAtRequest, provider.studyItems) →
    //     identify items where inputs changed while calc was in flight (stale results).
    //  2. For non-stale items: merge result.items[idx] into provider.studyItems.
    //  3. markDescendantsFailedForFailedItems({ plan, studyItems: merged, ... })
    //  4. restoreMissingCalculationStates(plan, merged, previousCalculationStates)
    //  5. enforceRollupOutOfSyncForIndices(affectedAncestorIndices, merged)
    //  6. Call provider.setTreeItems(merged).
    // Concurrent-call safety: detectInputChanges identifies items whose inputRevision
    // changed since the request was built — those items' results are discarded and their
    // previousCalculationStates restored. This handles the case where a second debounce
    // fires before the first fetch completes.

    provider.setTreeItems(updatedStudyItems);
    // Persist to Firestore. This includes items whose calculationState.status is "failed"
    // (calc returned a failure for an individual item). "Failure" here = API returned a
    // result with status:"failed" for that item — NOT a thrown network error (see catch).
    await setStudy(dbRef.current, dataProviderRef.current.studyItems);
  } catch {
    // Network/server error — silent failure: restore previous calculationStates, no toast.
    // We do NOT call setStudy here: writing restored (pre-calc) states would overwrite
    // any Firestore data written by a concurrent user or session.
    const p = dataProviderRef.current;
    const restored = { ...p.studyItems };
    for (const idx of plan) {
      if (restored[idx]) restored[idx] = { ...restored[idx], calculationState: previousCalculationStates[idx] };
    }
    p.setTreeItems(restored);
  } finally {
    setIsCalculating(false);
  }
}, []); // stable — reads only from refs

failedItems — derived study-wide

const failedItems = useMemo(() => {
  const result: FailedItemInfo[] = [];
  for (const item of Object.values(dataProvider.studyItems)) {
    if (!item || item.calculationState?.status !== "failed") continue;
    result.push({
      index: item.index,
      name: (item.information as { name?: string } | undefined)?.name ?? item.index,
      type: item.type,
      errorMessage: item.calculationState.error?.message ?? "Unknown error",
    });
  }
  return result;
}, [dataProvider.studyItems]);
Stale failures during recalculation: When a new calc starts, buildRunningItems sets each plan item's calculationState.status to "running" via provider.setTreeItems(). This clears the "failed" status on those items before the fetch begins, so failedItems will be empty during the calculation and the failure modal will close. Failures only re-appear if the new run also produces failures.

syncStatus: Derived via getSyncStatusLabel(studyRootItem, dataProvider.studyItems) — memoized on studyItems. studyRootItem is dataProvider.studyItems[dataProvider.getStudyIndex()].
