Inherited Field Propagation on Equipment Clear feat/auto-hac-calculation

Implementation Plan · nEXus · 2026-05-25 · Revised: A1b approach

Executive Summary

When a user clears pressure or temperature on an EquipmentItem, descendant Scenarios with inheritPressure: true / inheritTemperature: true silently retain their old value. The fix follows the existing codebase precedent established by the sourceAirVelocity / useGeneralAreaVelocity pattern: when the parent value is missing, the inherit toggle is automatically turned OFF, leaving the scenario's last known value as an editable override.

This approach requires no schema changes — all calculation inputs remain required numbers throughout. The fix touches 3 files across 3 logical layers (form sync, in-memory cascade, calculation guard). Tasks B and C are fully independent and can run in parallel.

shouldDirty: true — why it matters

Setting shouldDirty: true, shouldTouch: true matches the sourceAirVelocity precedent and ensures useAutoSaveFormData treats the toggle-off as a real change, persisting inheritTemperature: false to in-memory state. The existing sync uses shouldDirty: false (user-neutral propagation); a forced toggle-off should be treated as a meaningful state change.

In-Memory Cascade for Unmounted Scenarios
study-tree-context-provider.tsx Independent, large file — care needed

Handles scenarios whose forms are not currently open. The cascade sets inheritPressure/inheritTemperature = false in-memory so that: a) any subsequent form open loads with the correct state, and b) the calculation (triggered 1000ms after saveFormData) sees the correct flags.

Location: inside saveFormData, after the descendant out-of-sync marking block (~line 1221), before this._studyItems = finalStudyItems (~line 1251). 

// NEW BLOCK — insert after "CASCADE DOWN" out-of-sync marking, before this._studyItems = finalStudyItems
if (section === "hac" && itemWithRevision.type === "equipmentItem") {
  const prevHac = previousItem.hac as Record<string, unknown> | undefined;
  const newHac  = itemWithRevision.hac as Record<string, unknown> | undefined;

  const pressureCleared =
    typeof prevHac?.pressure === "number" && newHac?.pressure === undefined;
  const temperatureCleared =
    typeof prevHac?.temperature === "number" && newHac?.temperature === undefined;

  if (pressureCleared || temperatureCleared) {
    // getDescendantItemsByType from lib/study-tree-traversal.ts (already imported)
    const scenarioDescendants = getDescendantItemsByType(
      itemWithRevision.index,
      "scenario",
      finalStudyItems
    );

    for (const descendant of scenarioDescendants) {
      const hacData = descendant.hac as Record<string, unknown> | undefined;
      if (!hacData) continue;

      let updatedHac = { ...hacData };
      let didChange = false;

      if (pressureCleared && hacData.inheritPressure === true) {
        updatedHac = { ...updatedHac, inheritPressure: false };
        didChange = true;
      }
      if (temperatureCleared && hacData.inheritTemperature === true) {
        updatedHac = { ...updatedHac, inheritTemperature: false };
        didChange = true;
      }

      if (didChange) {
        finalStudyItems = {
          ...finalStudyItems,
          [descendant.index]: { ...descendant, hac: updatedHac },
        };
      }
    }
  }
}
// END new cascade block

Value is NOT cleared

The cascade sets the flag to false but leaves temperature and pressure values unchanged. The scenario's last inherited value becomes its explicit override — consistent with the A1b UX. Only fires on CLEAR (number→undefined). Value changes (number→number) are already handled at calc time by the existing inheritance block.

Risks & Edge Cases

Medium Timing: calc fires before cascade

Equipment autosave debounce: 500ms. Cascade runs inside saveFormData (sync). Calc debounce: 1000ms — triggered as microtask after saveFormData. So cascade always runs before calculation. Task B guard is a safety net for edge cases (e.g., direct tree manipulation bypassing saveFormData).

Medium User re-enables toggle immediately

If user re-enables inherit toggle after auto-off: the useEffect fires again immediately, sees parentTemperature === undefined, and auto-turns-off again. This is correct — the user is guided to restore the equipment value first. No infinite loop (the useEffect guard if (!inheritTemperature) return catches the settled state).

Low User-defined scenarios

User-defined scenarios have inheritTemperature: true (from BaseBsScenarioHacSchema) but no temperature or pressure fields. The Task B guard uses "temperature" in scenarioClone.hac to skip these. Task C useEffects have no temperature/pressure fields in their forms, so setValue has no effect. Task E cascade will still set inheritTemperature: false on User-defined scenarios — this is harmless (the flag has no functional effect for them).

Low Cascade modifies finalStudyItems mid-build

Task E modifies finalStudyItems after out-of-sync marking but before this._studyItems = finalStudyItems. The cascade directly modifies the map — no calls to saveFormData, no recursion. Safe.

Low Phast scenarios

PhastScenarioHacSchema has both temperature and pressure at the top level with the same inherit flags. Tasks B, C, and E are HAC-type-agnostic — they check the flags regardless of hacType. No special handling needed.

Low No schema changes — zero type regressions

temperature/pressure remain number (not number | undefined). No TypeScript audit needed. No downstream consumers affected.
