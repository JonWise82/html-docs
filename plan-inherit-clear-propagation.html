Inherited Field Propagation on Equipment Clear feat/auto-hac-calculation

Implementation Plan · nEXus · 2026-05-25

Executive Summary

When a user clears the pressure or temperature field on an EquipmentItem, descendant Scenarios that have inheritPressure: true / inheritTemperature: true silently retain their old value rather than reflecting the cleared state. The same bug exists in three layers: the live form sync (useEffect), the form-load default construction (buildHacDefaultValues), and the calculation service (which silently falls back to stale stored data instead of producing an error).

The fix touches 5 files across 4 logical layers, adds conditional Zod validation with a custom error message, cascades the cleared state through in-memory StudyTreeDataProvider state for unmounted scenario forms, and guards the calculation service with an explicit early-exit error. Two tasks are fully independent and can be implemented in parallel.

       ▼

2. Add superRefine to BsScenarioHacSchema

The existing BsScenarioHacSchema already has a .superRefine() for Indoor ventilation validation (lines 1111–1130). Add temperature and pressure checks to that same .superRefine(): 

// Extend the existing .superRefine() on BsScenarioHacSchema
// (already checks ventilationInefficiency and xcrit for Indoor)
.superRefine((data, ctx) => {
  // --- EXISTING Indoor ventilation checks (preserve as-is) ---

  // --- NEW: Inherited-but-missing temperature ---
  if ("temperature" in data) {
    const temp = data.temperature;
    if (temp === undefined || (typeof temp === "number" && Number.isNaN(temp))) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        path: ["temperature"],
        message: data.inheritTemperature
          ? "Equipment temperature is not set — restore the value or disable 'Use Temperature from Equipment Item'"
          : "Temperature is required",
      });
    }
  }

  // --- NEW: Inherited-but-missing pressure ---
  if ("pressure" in data) {
    const pres = data.pressure;
    if (pres === undefined || (typeof pres === "number" && Number.isNaN(pres))) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        path: ["pressure"],
        message: data.inheritPressure
          ? "Equipment pressure is not set — restore the value or disable 'Use Pressure from Equipment Item'"
          : "Pressure is required",
      });
    }
  }
})

Note: "temperature" in data is true only for BsEvaporatingPoolSchema and BsPressurisedGasSchema variants. "pressure" in data is true for BsPressurisedLiquidSchema and BsPressurisedGasSchema. BsUserDefinedSchema has neither, so both checks are silently skipped.

What happens after this change

When equipment temperature is cleared while the scenario form is open:

  1. useEffect fires → setValue("temperature", undefined, {shouldDirty:false})
  2. RHF form state: temperature = undefined
  3. Zod superRefine (Task A) fires → custom error shown on the disabled field
  4. useAutoSaveFormData fires (it does NOT check validity) → saves temperature: undefined to dataProvider in-memory state

In-Memory State Cascade for Unmounted Scenarios
study-tree-context-provider.tsx Depends on Task A

Tasks C and D handle scenarios whose forms are currently open or are subsequently opened after equipment save. Task E handles scenarios that are never reopened before the user presses Save — their in-memory state needs to be updated so stale data is never persisted to Firestore.

Note: Firestore is only written on explicit Save button press (save-study-modal.tsx). useAutoSaveFormData only updates in-memory state. The cascade below updates in-memory state for all affected closed scenarios at the moment of equipment save.

Location

Inside saveFormData (line ~1146), after finalStudyItems is assembled and the out-of-sync marking completes — before this._studyItems = finalStudyItems at line 1251. Specifically, inject the cascade after the descendant out-of-sync marking block (lines 1208–1221).

Implementation

// --- NEW BLOCK: cascade cleared equipment values to linked scenarios ---
// Insert after the existing "CASCADE DOWN: Mark all descendants as out-of-sync" block
if (
  section === "hac" &&
  itemWithRevision.type === "equipmentItem"
) {
  const prevHac = previousItem.hac as Record<string, unknown> | undefined;
  const newHac  = itemWithRevision.hac as Record<string, unknown> | undefined;

  const pressureCleared =
    typeof prevHac?.pressure === "number" && newHac?.pressure === undefined;
  const temperatureCleared =
    typeof prevHac?.temperature === "number" && newHac?.temperature === undefined;

  if (pressureCleared || temperatureCleared) {
    // getDescendantItemsByType is available via lib/study-tree-traversal.ts
    // It is already imported in this file. Use the updated finalStudyItems.
    const scenarioDescendants = getDescendantItemsByType(
      itemWithRevision.index,
      "scenario",
      finalStudyItems
    );

    for (const descendant of scenarioDescendants) {
      const hacData = descendant.hac as Record<string, unknown> | undefined;
      if (!hacData) continue;

      let updatedHac = { ...hacData };
      let didChange = false;

      if (pressureCleared && hacData.inheritPressure === true) {
        updatedHac = { ...updatedHac, pressure: undefined };
        didChange = true;
      }
      if (temperatureCleared && hacData.inheritTemperature === true) {
        updatedHac = { ...updatedHac, temperature: undefined };
        didChange = true;
      }

      if (didChange) {
        finalStudyItems = {
          ...finalStudyItems,
          [descendant.index]: {
            ...descendant,
            hac: updatedHac,
          },
        };
      }
    }
  }
}
// --- END new cascade block ---

Utility to use

getDescendantItemsByType from lib/study-tree-traversal.ts — already imported in this file (see CLAUDE.md). Includes cycle detection and depth guards. Do NOT write a manual parent/children traversal.

Why only cascade on clear (not on every value change)

The "equipment changed to a new number" case is already handled at calculation time by bs-calculation-service.ts lines 651–669, and at form-open time by buildHacDefaultValues. Cascading every equipment HAC write to all descendant scenarios would duplicate that logic and add unnecessary write overhead. Only clearing needs an explicit cascade because the existing mechanism silently skips it.

Risks, Edge Cases & Preserved Behaviour

High TypeScript type regressions from optional fields

Making temperature/pressure optional() changes inferred types throughout the codebase. The calculation engine reads these fields. Mitigation: Run npm run typecheck after Task A before proceeding. The calc service guard (Task B) is designed to prevent undefined values ever reaching downstream calculation code.

High superRefine overrides field-level Zod errors

With .optional(), Zod's built-in number validation won't fire for undefined. The superRefine covers undefined but not NaN from coercion of empty strings. Verify ControlledUnitField sends undefined (not empty string) when cleared so Zod's .coerce.number() doesn't silently produce NaN.

Medium Cascade modifies finalStudyItems mid-build

Task E modifies finalStudyItems after the out-of-sync marks but before this._studyItems = finalStudyItems. Ensure the cascade does NOT call saveFormData recursively (it directly modifies the map — no recursion risk).

Medium shouldDirty: false and autosave interaction

The useEffect fix uses shouldDirty: false, shouldTouch: false to avoid marking the form as user-modified. Despite this, useAutoSaveFormData fires on every useWatch reference change regardless of dirty state — confirmed by reading form-hooks.tsx. The undefined value WILL be persisted to in-memory state.

Low BsUserDefinedSchema — no temperature/pressure

User-defined scenarios have inheritTemperature: true (from base schema) but no temperature field. The "temperature" in data guard in superRefine and "temperature" in scenarioClone.hac in the calc service correctly skip these scenarios.

Low Phast scenarios

PhastScenarioHacSchema has both fields at the top level. Task A adds a separate superRefine. Tasks C and D apply to all scenario types (the useEffect and buildHacDefaultValues are HAC-type-agnostic). Task E cascade applies to all scenario descendants regardless of HAC type.

Low Existing "parent has value" path unaffected

The fix only removes an undefined early-return guard. When parent has a value (the normal case), the logic is unchanged — the equality check if (currentTemperature === parentTemperature) return; still short-circuits no-op updates.

Low validate-inputs.ts — already guarded

validate-inputs.ts checks hac.temperature != null && typeof hac.temperature === "number" before calling validateTemperature. No change needed — undefined is silently skipped. The calc service guard (Task B) fires before this code is reached.

Low Backwards compatibility — existing Firestore data

All existing scenario documents in Firestore have valid numbers for temperature/pressure (they were required before). The schema change to optional is backwards-compatible — existing numbers still parse successfully.
